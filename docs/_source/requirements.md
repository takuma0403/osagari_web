# 佐賀大お下がりフリマ 要件定義書

## 概要

佐賀大学の学生だけが使える、お下がり品の売買アプリです。教科書を中心に、家具・家電・ゲーム機など何でも出品できます。

アプリが担うのは、商品の登録・管理、一覧と検索、代金のやり取りの管理です。受け渡しと連絡は当事者同士で行い、連絡には学内アカウントのTeamsを使ってもらいます。

- **対象外**：チャット、商品Q&A、配送、受け渡しの代行
- **フェーズ1の決済**：モック（実際のお金は動かさない）

## ユーザー・認証・アカウント期限

アカウントは `@edu.cc.saga-u.ac.jp` のメールアドレスでのみ作成できます。有効期限は学籍番号から自動で設定します。

### 登録・ログイン

- **新規登録**：メールアドレスを入力すると、ドメインが `@edu.cc.saga-u.ac.jp` かどうかを確認し、6桁の認証コードをメールで送ります。コードの認証に成功したらパスワードを設定し、アカウントを作成します。
- **通常のログイン**：メールアドレスとパスワードでログインします。
- **定期的な再確認**：最後にコードで確認してから30日たった場合や、初めて使う端末の場合は、パスワードに加えてメールの認証コードの入力を求めます。卒業などで大学のメールが使えなくなると、この再確認ができずログインできなくなります。
- **パスワードの再設定**：メールの認証コードで本人確認をしてから、新しいパスワードを設定します。
- メールアドレスの@より前を学籍番号として保存します。
- 詳しい仕組みと流れの図は、技術構成ドキュメントの「認証」の章にあります。

### 学籍番号から推定する情報

- 学籍番号から入学年度と学部を推定し、ユーザー情報に登録します。
- 推定した学部は、検索の絞り込みや出品者の表示に使えます。

### 有効期限と失効

- 有効期限は「入学年度 + 修業年限（医学部医学科は6年、それ以外は4年）」の3月31日を初期値にします。
- 退学の申請があった場合は、その時点でアカウントを削除します。
- 申請がなければ、通常の期限で失効させます。
- 延長の仕組み（留年、6年制の学科、大学院進学など）は後で検討します。

### 学籍番号の構成と学部コード

学部生の学籍番号は8桁で、「入学年度（西暦の下2桁）＋学部・学科コード（3桁）＋連番（3桁）」で構成されます（[2019年度 全学教育機構 履修の手引き](https://www.sc.admin.saga-u.ac.jp/tebiki-h31-kyoyo.pdf)）。メールアドレスは「学籍番号@edu.cc.saga-u.ac.jp」です（[LiveCampus利用説明資料](https://www.sc.admin.saga-u.ac.jp/livecampus_setumei.pdf)）。

│   └ 学部・学科コード（例：理工学部 理工学科）

### 教職員の利用（検討保留）

教職員も利用できるようにしたいと考えています。詳細の検討は保留中で、現時点で決まっているのは次の前提だけです。

- 教職員用の画面とAPIは、学生用とは分けて作ります。
- 教職員のメールアドレスは学籍番号の形式（数字8桁）ではないため、数字以外も受け付ける必要があります。

## 学生証登録

出品するには学生証画像の登録が必須です。画像は不正行為を抑止するため、アカウントの失効・削除後も3年間保持します。

- 出品者は学生証画像をアップロードし、管理者の承認後に出品できるようになります。
- 審査では、学生証の番号とログインに使ったメールアドレスの学籍番号が一致するかを確認します。
- 画像は非公開のストレージに暗号化して保存し、閲覧できるのは管理者だけにします。閲覧した記録も残します。
- アカウントの失効・削除から3年が経過したら、画像を自動で削除します。運営は利用者間のトラブルを原則として仲裁しませんが、問題が起きたときに当事者を特定できるよう保持します。
- 保持する目的と期間は、利用規約とプライバシーポリシーに明記します。

## 出品・商品管理

出品には、すべてのカテゴリで共通の項目を入力します。カテゴリによっては追加の項目も入力できます。

| 区分 | 項目 |
| --- | --- |
| 共通 | 写真（複数枚）、タイトル、カテゴリ、状態、価格（円）、説明文、受け渡し希望キャンパス（本庄・鍋島） |
| 教科書・参考書 | 授業名、担当教員、ISBN、書き込みの有無 |
| 家具・家電 | サイズ、動作確認の有無 |
| ゲーム・その他 | 共通項目のみ |

- 商品のステータスは「下書き → 公開中 → 購入希望あり → 取引中 → 取引完了」と進みます。出品者はいつでも「取り下げ」にできます。
- 出品者は、自分の出品一覧から編集、取り下げ、再出品ができます。
- 取引中の商品は、価格などを編集できないようにします。

## 一覧・検索・共有

紹介機能は、公開中の商品の一覧ページとして実装します。それに加えて、検索とリンクによる共有に対応します。

- **一覧ページ**：公開中の商品を新着順に並べ、カテゴリ別に切り替えられるようにします。
- **検索**：キーワード、カテゴリ、授業名、価格帯、キャンパス、状態で絞り込みます。
- **共有リンク**：商品ページごとに固定のURLを持たせ、コピーやシェアのボタンを置きます。コピーするときは、商品名・価格・状態とURLをまとめた文章にします。リンクのプレビューが表示されない環境でも、内容が伝わるようにするためです。
- 共有リンクをログインしていない人が開いたときの扱い（ログイン画面へ誘導するか、概要だけ見せるか）は未定です。

## 取引フロー

購入希望の時点ではカードの枠を確保するだけで、出品者が承認した時点で代金を預かり、購入者がQRを読み取った時点で出品者の売上として確定します。連絡と受け渡しはアプリの外で行います。

受け渡しが成立しなかった場合は、双方の同意で取引をキャンセルし、代金を返金して商品を公開中に戻します。

### 購入希望と出品者の承認

出品者が承認するまで学籍番号は開示しません。これにより、出品者が取引相手を選べるようになります。

1. 購入者が「購入希望」を出すと、支払い方法の枠を確保します（カードのオーソリ）。この時点では代金は動きません。
2. 1つの商品に複数の購入希望を受け付けます。出品者は一覧から1人を選んで承認します。
3. 承認されると代金を預かり、取引成立として双方の学籍番号をシステムが開示します。選ばれなかった購入希望は自動で却下し、枠を解放します。
4. 48時間以内に承認されなかった購入希望は期限切れとし、枠を解放します。カードのオーソリには有効期限があるため、この期限は短めにしています。

商品のステータスは「公開中 → 購入希望あり → 取引中 → 取引完了」と進みます。購入希望ありの間も、ほかの人は購入希望を出せます。

### 出品者への確認モーダル

取引が成立したとき、出品者に次の内容のモーダルを表示します。

> 入金は、受け渡しの場で購入者がQRコードを読み取った時点で確定します。受け渡しの際は、忘れずにQRコードを読み取ってもらってください。

- 出品者が「確認しました」を押した日時を記録します。
- これ以降、QRの読み取り忘れによる不利益について運営は責任を負いません。この旨を利用規約にも明記します。

### 受け渡し完了の確認（QRコード）

受け渡しの場で出品者がQRコードを表示し、購入者がそれを読み取ると、受け渡し完了と出品者への代金の確定が同時に行われます。代金が動くきっかけを購入者の操作にすることで、商品を受け取る前にお金が渡ることを防ぎます。

1. 出品者が取引詳細画面で「受け渡しQRを表示」を押すと、その取引専用のQRコードが表示されます。
2. 購入者は商品を確認してから、取引詳細画面の「QRを読み取る」でコードを読み取ります。
3. サーバーで照合できたら、取引を「受け渡し完了」にし、手数料を引いた金額を出品者の売上として確定します。
4. 双方の画面に完了が表示されます。

**QRコードの仕様**

- 中身は取引IDと使い捨てのトークンだけにします。個人情報や金額は含めません。
- 有効期限は短くし（例：5分）、期限が切れたら表示し直せるようにします。
- 読み取れるのは、その取引の購入者としてログインしている人だけにします。ほかの人が読み取ってもエラーにします。
- 一度使ったトークンは無効にし、同じ取引が二重に完了しないようにします。
- カメラが使えない場合に備え、QRの下に6桁の確認コードも表示し、手入力でも完了できるようにします。

**QRを読み忘れた場合**

- 出品者が取引詳細画面から「完了リンク」か「6桁の完了コード」を発行し、Teamsで購入者に送ります。
- 購入者がログインした状態でリンクを開くか、コードを入力すると受け渡し完了になります。完了させるのが購入者の操作であることはQRと同じです。
- リンクとコードの有効期限は24時間とし、一度使ったら無効にします。
- 購入者が完了する前に「商品を受け取りましたか？」という確認を表示し、受け取る前に完了させられることを防ぎます。QRの読み取り時も同じ確認を表示します。

### キャンセルのルール

- 取引成立後のキャンセルは、双方が同意した場合にだけできます。どちらか一方だけではキャンセルできません。
- 受け渡し完了後は、アプリ上でキャンセルや返金はできません。
- キャンセルの回数を記録し、回数が多い利用者には警告やアカウント停止で対応します。

### 自動完了（暫定・導入するか要検討）

**この仕組みは暫定案で、導入するかどうかを含めて検討中です。**

購入者が商品を受け取った後にQRを読み取らない場合、双方同意のキャンセルルールのもとでは代金が預かられたまま止まってしまいます。これを防ぐ案として、次の仕組みを考えています。

- 取引成立から7日経過したら、自動で受け渡し完了にして出品者の売上を確定します。
- 期限の前に、双方へ催促の通知を送ります。
- 運営は仲裁しません。購入者が「受け取っていない」と申告しても、自動完了は止めません。

導入しない場合は、止まった取引をどう扱うか（運営が手動で処理するか、双方同意を待ち続けるか）を別に決める必要があります。

## 決済・手数料・出金

フェーズ1ではモックで実装します。ただしデータの持ち方は、本番の決済代行サービスにそのまま置き換えられる形にしておきます。

### 本番で目指す要件

| 項目 | 要件 |
| --- | --- |
| 支払い方法 | クレジットカード、PayPay |
| 売上の受け取り先 | 銀行口座、またはPayPay（ポイント・残高） |
| 手数料 | アプリ側で差し引く（料率は未定） |
| 代金の流れ | 購入希望で枠を確保し、出品者の承認で預かり、QRによる受け渡し完了で出品者の売上として確定する |

### お金の計算

- 出品者の売上 = 商品価格 − 手数料
- 手数料率は管理画面から変更できるようにし、取引ごとに適用した料率を記録します。

### 調査が必要なこと

- マーケットプレイス型の決済代行サービスで、クレジットカードとPayPayの両方に対応しているもの。
- 出品者への送金先として、PayPayを指定できるかどうか。
- 運営が売上金を一時的に預かる形が、資金移動業などの規制に当たらないかどうか。決済代行サービスのプラットフォーム機能に預かりを任せる構成を前提に考えます。

### 決済サービスの候補（検討段階・未決定）

**この節は検討段階のメモで、採用は決まっていません。** 2026年10月時点の調査で、条件に最も近いのはStripe Connectです。ただし、PayPayで売上を受け取る仕組みは現実的ではありません。

| 候補 | 支払い方法 | 手数料の差し引き・分配 | 注意点 |
| --- | --- | --- | --- |
| [Stripe Connect](https://docs.stripe.com/changelog/clover/2025-11-17/paypay-connect) | カード、PayPay | 取引ごとにプラットフォーム手数料を差し引ける | 出品者ごとのPayPay利用には、商品の種類と特定商取引法の表記URLが必要。[PayPayの審査には数週間かかる](https://support.stripe.com/questions/accepting-paypay-payments-for-japan-based-stripe-accounts) |
| [PAY.JP Platform](https://paymentnavi.com/?p=74246) | カード（PayPayは要確認） | 出品者の審査、売上の精算、利用料の回収を代行 | PAY.JP本体は[2026年2月にPayPayに対応](https://www.issoh.co.jp/tech/details/15722/)。Platform機能で使えるかは問い合わせが必要 |

- **PayPayでの受け取り**：[PayPayポイントAPI](https://paypay.ne.jp/biz/api/)は法人限定で、月100万円以上の付与が推奨されています。付与されたポイントは出金も譲渡もできないため、売上の受け取り先には向きません。PayPay銀行の口座への振込なら、銀行口座として扱えます。
- **出品者の登録負担**：どちらの候補でも、出品する学生一人ひとりが本人確認付きのアカウントを作る必要があります。
- **運営側の準備**：個人事業主か法人として、特定商取引法の表記が必要になります。
- **法規制**：2026年6月施行の改正資金決済法でエスクローは適用除外とされましたが、[出資法の預り金規制にも別途照らす必要があります](https://www.issoh.co.jp/column/details/17260/)。本番に移る前に専門家に確認します。

## 管理者機能

管理者は、出品者の承認、トラブル対応、お金まわりの設定を担当します。

- 学生証の審査（承認・差し戻し）と、画像の閲覧記録の確認
- 出品の停止と、ユーザーのアカウント停止
- 取引状況の確認と、キャンセル・返金（モック）の手動対応
- 手数料率の設定
- 退学申請の受け付けと、アカウントの削除
- 有効期限の手動変更（延長の仕組みができるまでの暫定対応）

## データモデル

主なデータは6種類です。決済まわりは、本番の決済代行サービスのIDを後から持たせられる形にしておきます。

| データ | 主な項目 |
| --- | --- |
| User（ユーザー） | ID、メールアドレス、学籍番号、入学年度、学部、有効期限、状態（有効・停止・失効・削除）、出品者の承認状態 |
| StudentCard（学生証） | ユーザーID、画像の保存場所、審査状態、審査した人、審査日時、閲覧記録、削除予定日（失効・削除日 + 3年） |
| Item（商品） | 出品者ID、カテゴリ、タイトル、説明文、状態、価格、キャンパス、カテゴリ別の追加項目、ステータス、共有用ID |
| ItemImage（商品画像） | 商品ID、画像の保存場所、表示順 |
| Transaction（取引） | 商品ID、購入者ID、出品者ID、金額、手数料率、手数料、出品者の売上、ステータス、ステータス（購入希望・却下・期限切れ・取引中・キャンセル・完了）、承認期限、学籍番号を開示した日時、出品者が確認モーダルに同意した日時、受け渡しトークン（QR・リンク・コード）とその有効期限、キャンセルへの双方の同意日時、受け渡しが完了した日時と完了方法（QR・リンク・コード・自動） |
| Payment（決済・出金） | 取引ID、種別（支払い・返金・出金）、支払い方法、金額、ステータス、外部サービスのID（モックでは空） |
