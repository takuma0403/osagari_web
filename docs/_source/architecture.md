# 佐賀大お下がりフリマ 技術構成

要件定義書とは別に、技術の選定と構成をまとめるドキュメントです。費用をできるだけかけないことを優先しています。

## 構成の全体像

Firebase Hosting は静的ファイルの配信だけを担当し、ログイン、取引、トークンの照合などの処理はすべて Cloud Run のAPIで行います。

## フロントエンド

Vite + React のSPAを Firebase Hosting に置きます。ログイン必須のアプリなので、検索エンジン向けのSSRは必要ありません。Firebase Hosting は無料のSparkプランで使えます。

| 選択肢 | 費用 | 判断 |
| --- | --- | --- |
| Vite + React（SPA）を Firebase Hosting に置く | 無料（Sparkプランで可） | **採用** |
| Next.js を Firebase App Hosting に置く | Blazeプラン（従量課金）が必須。無料枠あり | SSRが必要になったら検討 |
| Next.js を Vercel の Hobby プランに置く | 無料だが非商用に限る | **不採用**。手数料を取るので商用扱いになり、有料のProプランが必要 |

- Firebase Hosting 単体では Next.js のSSRは動きません。Next.js をSSRで使うには、Blazeプランが前提の App Hosting を使う必要があります（[Firebase公式ブログ](https://firebase.blog/posts/2024/05/app-hosting-vs-hosting)）。
- Vercel の Hobby プランは非商用の個人利用に限られ、商用利用には Pro 以上が必要です（[Vercel Fair Use Guidelines](https://vercel.com/docs/limits/fair-use-guidelines)）。
- **ルーティング**：画面遷移は React Router で行います。商品ページの共有リンク（`/items/:id`）もSPAのルートとして扱い、Firebase Hosting では `/api/**` 以外のすべてのパスを `index.html` に返す設定にします。
- **共有リンクのプレビュー**：SPAのため、TeamsやLINEにリンクを貼っても商品ごとのタイトルや画像のプレビュー（OGP）は表示されず、アプリ共通の表示になります。リンクを開けば商品ページは問題なく表示されます。その代わりに、共有ボタンでは商品名・価格・状態とURLをまとめた文章をコピーできるようにし、リンクを貼るだけで内容が伝わるようにします（例：「【お下がり】線形代数学の教科書 ¥1,500（書き込みなし） https://…/items/123」）。スマホでは Web Share API で共有シートも開けるようにします。
- **QRコード**：表示はQR生成ライブラリ、読み取りはブラウザのカメラを使うライブラリで行います。カメラの利用にはHTTPSが必要ですが、Firebase Hosting は標準でHTTPSです。

## API

APIは Cloud Run で動かし、Firebase Hosting の rewrites で `/api/**` を転送します。フロントとAPIが同じドメインになるので、CORSやサードパーティCookieの問題を避けられます。

- **言語**：Go を使い、Webフレームワークは Echo にします。
- **リージョン**：東京（asia-northeast1）にします。
- **最小インスタンス数**：0にします。待機中の費用はかかりませんが、しばらくアクセスがないと初回の応答が遅れます。Go は単一のバイナリで起動が速いため、この遅れは小さく抑えられます。
- **無料枠**：Cloud Run には毎月、200万リクエストと18万vCPU秒の無料枠があります（[Cloud Run pricing](https://cloud.google.com/run/pricing)、us-central1基準）。学内アプリの規模なら収まる見込みです。
- **秘密情報**：Gmailのアプリパスワード、Tursoの接続トークン、セッション署名鍵は Secret Manager に保存します。

**Cookieの注意点**：Firebase Hosting から Cloud Run に転送するとき、Cookieは `__session` という名前のもの以外すべて削除されます（[Firebase: Manage cache behavior](https://firebase.google.com/docs/hosting/manage-cache)）。そのため、ログインセッションのCookie名は `__session` にします。

APIが担当する主な処理は次のとおりです。

- 新規登録、パスワードによるログイン、認証コードの発行と照合、パスワードの再設定、セッション管理
- 商品の登録、一覧、検索
- 購入希望、承認、キャンセルなどの取引の状態遷移
- 受け渡しトークン（QR・リンク・コード）の発行と照合
- 画像アップロード用の署名付きURLの発行
- 決済処理（当面はモック）
- 管理者向けの処理（学生証の審査、ユーザーの停止、手数料率の設定など）

**教職員用のAPI（検討保留）**：教職員にも対応する予定で、教職員用の画面とAPIは学生用と分ける前提です（例：`/api/staff/**`）。詳細は要件定義書の「教職員の利用」で検討中です。

## 認証

普段はメールアドレスとパスワードでログインし、新規登録時と定期的な再確認のときだけ、メールで届く6桁のコードを使います。大学のMicrosoftアカウントでのログインは使えないため自前で実装し、メールは Gmail のSMTPで送ります。

&#91;embedded content: ログインの流れ · 新規登録と通常のログイン\]

### コードを使う理由

メール内のリンクを開く方式ではなく、6桁のコードを入力する方式にします。

- 大学のMicrosoft 365では、セキュリティ機能がメール内のリンクを自動で開いて確認することがあります。一度しか使えないリンクだと、利用者が開く前に使用済みになるおそれがあります。
- PCで手続きしながらスマホでメールを見る、といった使い方でもそのまま使えます。

### 新規登録

1. 利用者がメールアドレスを入力します。サーバーで `^\d{8}@edu\.cc\.saga-u\.ac\.jp$` に一致するか確認し、一致しなければ送信しません。
2. 6桁のコードを生成し、ハッシュ化してDBに保存したうえで、Gmail SMTPで送ります。有効期限は10分です。すでに登録済みのアドレスには、コードの代わりに「登録済みです」という案内を送り、画面上はどちらも同じ表示にします。登録の有無を画面から調べられないようにするためです。
3. コードが一致したら、パスワード設定用の一時トークン（15分有効）を発行します。
4. 利用者がパスワードを設定すると、アカウントを作成します。学籍番号から入学年度、学部、有効期限を計算して登録し、そのままログイン状態にします。

### 通常のログイン

1. 利用者がメールアドレスとパスワードを入力します。
2. パスワードが一致したら、次のどちらかに当てはまるか確認します。
   - 最後にコードで確認してから30日以上たっている
   - 初めて使う端末である
3. 当てはまる場合はメールで6桁のコードを送り、入力されたら確認日時を更新して端末を登録します。当てはまらなければ、そのままログインできます。
4. セッションを発行します。有効期間は30日です。

- **端末の識別**：Firebase Hosting を経由すると `__session` 以外のCookieが削除されるため、端末識別子はブラウザの localStorage に保存し、ログイン時にヘッダーで送ります。
- **卒業後の扱い**：卒業して大学のメールが使えなくなるとコードを受け取れないため、遅くとも30日後にはログインできなくなります。有効期限による失効を補う仕組みにもなります。

### パスワードの再設定

1. 利用者がメールアドレスを入力すると、6桁のコードを送ります。
2. コードが一致したら新しいパスワードを設定し、その利用者の既存のセッションをすべて無効にします。

### パスワードとセッションの扱い

- パスワードは argon2id でハッシュ化して保存します。長さは10文字以上とします。
- セッションIDは `__session` という名前のCookieに入れます（HttpOnly、Secure、SameSite=Lax）。セッションはDBで管理し、ログアウトや強制停止ですぐ無効にできるようにします。

### 不正対策と送信数の制限

- パスワードの入力ミスが10回続いたら、15分間そのアカウントのログインを止めます。
- 同じアドレスへのコード送信は1分に1回、1時間に5回までにします。
- コードの入力ミスは5回までとし、超えたらそのコードを無効にします。
- 無料のGmailアカウントは1日の送信数がおよそ500通までです。コードを送るのは登録時と再確認時だけなので通常は収まりますが、全体の送信数も記録して上限に近づいたら管理者に知らせます。

### Gmail SMTPの設定

- アプリ専用のGmailアカウントを作り、2段階認証を有効にしてアプリパスワードで送信します。
- Cloud Run からは587番ポート（STARTTLS）で接続します。25番ポートは使えません。
- 大学のメールで迷惑メールに振り分けられないか、運用前に実際に送って確認します。

**教職員への対応（検討保留）**：上の正規表現は学生（数字8桁）だけを受け付けます。教職員用には数字以外も受け付ける別の登録・ログインの経路を用意する前提ですが、受け付けるドメインなどの詳細は未定です。

## DB

DBは Turso（SQLite互換）を使います。無料プランでもスリープしないため、夏休みなどの利用が少ない時期にも止まりません。

| 項目 | 無料プランの上限 |
| --- | --- |
| ストレージ | 合計5GB |
| 読み取り | 月5億行 |
| 書き込み | 月1,000万行 |
| ポイントインタイム復元 | 1日分 |

出典：[Turso Pricing](https://turso.tech/pricing.md)、[freetier.co](https://freetier.co/directory/products/turso)

- **DBアクセス**：Go から GORM を使って Turso に接続します。GORM の SQLite 用ドライバに Turso（libSQL）のドライバを組み合わせて使う想定です。
- **マイグレーション**：golang-migrate で、SQLファイルとしてバージョン管理します。GORM の自動マイグレーション（AutoMigrate）は本番では使わず、スキーマの変更は必ずマイグレーションファイルで行います。
- **二重処理の防止**：購入希望の承認や受け渡しの完了は、「現在のステータスが想定どおりのときだけ更新する」条件付きの更新で行います。同じ商品を2人に承認したり、同じ取引を2回完了させたりすることを防ぎます。
- **バックアップ**：無料プランの復元は1日分しかないため、定期処理で毎日DBを書き出して Cloud Storage に保存します。
- **比較した候補**：Supabase の無料プランは、1週間アクセスがないとプロジェクトが一時停止するため見送りました。Render の無料Postgresは作成から30日で期限切れになるため、本番には使えません。

## ファイル保存

学生証と商品写真は Cloud Storage に保存し、バケットを分けます。どちらもブラウザから直接アップロードし、APIはアップロード用の署名付きURLを発行するだけにします。

| バケット | 公開範囲 | 閲覧方法 |
| --- | --- | --- |
| 商品写真 | ログインした利用者のみ | APIが短時間有効な署名付きURLを発行する |
| 学生証 | 非公開 | 管理者向けAPIだけが署名付きURLを発行し、閲覧の記録を残す |

- **画像の縮小**：アップロード前にブラウザで縮小・圧縮し、保存容量と転送量を抑えます（例：長辺1600px、JPEGまたはWebP）。
- **学生証の削除**：アカウントの失効・削除から3年たった画像を、定期処理でDBの削除予定日に従って削除します。
- **暗号化**：Cloud Storage は保存データを標準で暗号化しています。学生証のバケットには公開アクセス防止を設定し、誤って公開されないようにします。
- **リージョン**：Cloud Storage の常時無料枠（5GB）は米国の一部リージョンだけが対象です。東京リージョンにすると少額の保存料金がかかるので、どちらにするかは費用と表示速度を比べて決めます。

## 定期処理と決済モック

### 定期処理

Cloud Scheduler から Cloud Run の内部用エンドポイントを定期的に呼び出します。Cloud Scheduler の無料枠に収まるよう、ジョブは2つにまとめます。

| ジョブ | 間隔 | 処理内容 |
| --- | --- | --- |
| 短周期ジョブ | 15分ごと | 48時間たった購入希望の期限切れ処理と枠の解放、期限切れのログインコード・受け渡しトークンの削除、自動完了（暫定）と催促通知 |
| 日次ジョブ | 毎日深夜 | アカウントの失効、削除予定日を過ぎた学生証画像の削除、DBのバックアップ |

- 内部用エンドポイントは、Cloud Scheduler のサービスアカウントからの呼び出しだけを受け付けるようにします。

### 決済モック

決済は、処理の窓口（インターフェース）を1つ決め、当面はモックの実装を差し込みます。本番では、同じ窓口に Stripe Connect や PAY.JP の実装を差し替えます。

| 操作 | タイミング | モックでの動き |
| --- | --- | --- |
| 枠の確保 | 購入希望 | 成功したことにして記録する |
| 代金の確定（預かり） | 出品者の承認 | 記録する |
| 枠の解放 | 却下・期限切れ | 記録する |
| 返金 | 双方同意のキャンセル | 記録する |
| 売上の確定 | 受け渡し完了 | 手数料を引いた金額を出品者の売上として記録する |

- 本番の決済サービスからの通知（Webhook）を受けるエンドポイントは、最初から枠だけ用意しておきます。

## 費用の見込み

学内アプリの規模であれば、月の費用はほぼ0円で、かかっても数十円程度の見込みです。ただし Cloud Run と Cloud Storage を使うには Google Cloud の課金アカウントが必要です。

| サービス | 想定プラン | 月額の目安 |
| --- | --- | --- |
| Firebase Hosting | Spark（無料） | 0円 |
| Cloud Run | 無料枠内 | 0円 |
| Cloud Scheduler | 無料枠内（ジョブ2つ） | 0円 |
| Cloud Storage | 東京リージョンの場合は従量課金 | 数十円程度 |
| Turso | Free | 0円 |
| Gmail | 無料アカウント | 0円 |

- 課金アカウントには予算アラート（例：月1,000円）を設定し、想定外の課金にすぐ気づけるようにします。
- 有料プランが必要になる主なきっかけは、Gmailの送信上限（1日約500通）を超えたときと、Tursoの無料枠を超えたときです。
