# ADR 0025: 受け渡しQRと完了リンクのフラグメントを分ける、QR の生成・読み取りのライブラリ、出品者の画面への完了の反映

- 日付: 2026-10-25
- 状態: 採用（[ADR 0024](0024-handover-token-flow.md) の「完了リンクと受け渡しQRの中身」を置き換える）
- 関連する章ID: DEAL-3, FE, FE-1

## 背景

ADR 0024 では、完了リンクと受け渡しQRの中身をどちらも `/deals/{取引ID}/complete#t=<トークン>` とした。一方でサーバーは照合のときにトークンの種類（`qr`・`link`）の一致を求める。購入者がアプリの「QRを読み取る」ではなくスマホ標準のカメラで QR を読むと完了リンクの画面が開き、アプリは種類を見分けられないため `link` として送って 400 になる。

あわせて、#28 で QR の生成・読み取りのライブラリと、購入者が完了したことを出品者の画面にどう出すか（DEAL-3「双方の画面に完了が表示されます」）を決める必要があった。

## 決定

- 受け渡しQRの中身は `/deals/{取引ID}/complete#q=<トークン>`、完了リンクは `/deals/{取引ID}/complete#t=<トークン>` にする。完了の画面はフラグメントの名前で種類（`q` → `qr`、`t` → `link`）を決める。アプリ内の読み取りでは、同じ取引の `#q=` の URL だけを受け付ける。
- 完了の画面はフラグメントを読んだらすぐ URL から消す（履歴・画面共有に残さない）。
- QR の生成は `uqr`（依存なし・ESM）で行い、行列を SVG で描く。読み取りは出品画面の ISBN と同じ `@zxing/browser` を QR_CODE だけに絞って使い、読み取りを開いたときに動的に読み込む。
- 出品者が受け渡しQRを表示している間は、画面が前面にあるときだけ 5 秒ごとに取引を取り直し、完了になったら完了の表示に切り替える。

## 理由と検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| QR を `#q=`、リンクを `#t=` にする（採用） | 標準カメラで読んでも `qr` として完了でき、完了方法も正しく残る。app だけの変更で済む | ADR 0024 の形式を変える |
| `#t=` のまま、アプリ内の読み取りだけにする | 仕様を変えない | 標準カメラで読むと失敗し、受け渡しの場で迷う |
| サーバーで種類の違いを許す | URL を変えない | server の変更が要り、完了方法の記録があいまいになる |
| `uqr`（採用） | 依存なし・小さい・2026年も更新されている。行列を返すのでデザインどおりに描ける | 版が 0.x |
| `lean-qr` | 小さい・更新が新しい | 描画の API が独自 |
| `qrcode` | 定番 | 依存（pngjs・yargs など）があり、最終リリースが古い |
| 5秒ごとに取り直す（採用） | server の変更なし。表示中だけなので無料枠に収まる | 最大5秒遅れる |
| 手動で更新 | 通信が少ない | 「双方の画面に完了が表示」を満たしにくい |
