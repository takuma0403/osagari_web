# ADR 0006: 認証の秘密の値のハッシュ方式と学部の持ち方

- 日付: 2026-10-14
- 状態: 採用
- 関連する章ID: AUTHN-2, AUTHN-3, AUTHN-5, AUTH-4, DATA

## 背景

#8（認証のテーブルとメール送信の基盤）でテーブルを作るにあたり、仕様に書かれていない次の点を決める必要があった。

- AUTHN-5 はセッションを「DBで管理」とだけ書いており、セッションIDを平文で持つかハッシュで持つかが決まっていない。
- AUTHN-2 は認証コードを「ハッシュ化して保存」と書いているが、方式が決まっていない。
- AUTH-4 は「表にないコードは学部を『不明』として登録し、管理者が後から修正できる」としているが、学籍番号から取った値と修正後の値をどう持つかが決まっていない。

## 決定

- セッションIDは256ビットの乱数を Cookie `__session` に入れ、DB（`sessions.token_hash`）には SHA-256 の16進だけを保存する。端末識別子（`trusted_devices.device_hash`）も SHA-256 で保存する。
- 6桁の認証コード（`verification_codes.code_hash`）は argon2id（パスワードと同じパラメータ、ソルト付き）でハッシュ化する。
- `users` は `department_code`（学籍番号の3〜5桁目。NOT NULL）と `department`（AUTH-4 の表で確定した学部・学科。NULL は不明。管理者が修正する）の2列を持つ。

## 理由と検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| セッションIDを平文で保存 | 実装が簡単 | DB が漏れるとセッションをそのまま乗っ取られる |
| **セッションIDを SHA-256 で保存（採用）** | DB が漏れても乗っ取れない。乱数が十分長いのでソルトや低速ハッシュは不要で、ハッシュで検索できる | Cookie の値から毎回ハッシュを計算する（軽い） |
| 認証コードを SHA-256 で保存 | 速い | 100万通りしかないので、DB が漏れると一瞬で総当たりできる |
| **認証コードを argon2id で保存（採用）** | 総当たりの手間が大きい。パスワードと同じ実装を使える | 照合が遅い（送信と入力は回数が限られるので問題にならない） |
| 学部を `department_code` の1列だけで持つ | 列が少ない | 管理者が直すと、学籍番号から取った元の値が残らない |
| **学部を2列で持つ（採用）** | 元の値を残したまま、管理者が修正できる | 列が1つ増える |
