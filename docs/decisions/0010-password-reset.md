# ADR 0010: パスワード再設定の手続き・登録有無の隠し方・停止中の扱い

- 日付: 2026-10-15
- 状態: 採用
- 関連する章ID: AUTHN-4, AUTHN-2, AUTHN-3, AUTHN-5, AUTHN-6, API-1

## 背景

#11（パスワード再設定API）を実装するにあたり、AUTHN-4 は「メールのコードで本人確認をして新しいパスワードを設定し、既存のセッションをすべて無効にする」とだけ書いており、次の点が決まっていなかった。

- コードを確認してから新しいパスワードを受け取るまでを、どうやって同じ手続きに結びつけるか。
- 未登録・削除済みのアドレスに再設定を求められたとき、登録の有無を判別させない方法（AUTHN-2）。
- 設定した後にその端末をログイン状態にするか。Password 画面［再設定］は「変更すると、ほかの端末ではログアウトされます」と表示し、ボタンでホーム（Main）へ進む。
- 停止中・失効のアカウントが再設定しようとしたときの応答。

## 決定

- **手続き**：`POST /auth/password-reset/codes`（コード送信）→ `/codes/verify`（コード確認・一時トークン発行）→ `/complete`（新しいパスワードの設定）の3段階にする。コードは `verification_codes`（purpose = `password_reset`）、一時トークンは [ADR 0007](0007-signup-flow.md) の `password_setup_tokens`（purpose = `password_reset`、15分有効・一度だけ使える）を使う。新規登録のトークンでは再設定できない（用途を条件にして消費する）。
- **未登録・削除済みのアドレス**（ユーザーが選択）：ADR 0007 と同じく、コードを生成・保存してメールを1通送り、本文だけを「登録されていません」の案内にする（コードは書かない）。応答は常に `202`。
- **設定した後**（ユーザーが選択）：その利用者のセッションをすべて失効させ、この端末用の新しいセッションを発行して `__session` を返す。コードで本人確認をしたので最後の確認日時（`users.code_verified_at`）を更新し、`X-Device-Id` があればその端末を登録する。トークンの消費・パスワードの更新・セッションの失効と発行・端末の登録は1つのトランザクションで行う。
- **停止中・失効のアカウント**（ユーザーが選択）：コードは同じように送る（応答を揃える）。新しいパスワードの設定時に、停止中なら `403 account_suspended`、失効（有効期限の日を日本時間で過ぎた場合を含む）なら `403 account_expired` を返し、パスワードは変えない。トランザクションを戻すので一時トークンも使われずに残り、既存のセッションも変えない。削除済みは `400 invalid_setup_token`（未登録と同じ）。
- 新しいエラーコードは追加しない。

## 理由と検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| **一時トークンで結びつける（採用）** | 新規登録と同じ部品・同じ画面の流れで作れる。パスワードの入力をやり直してもコードは再入力不要 | — |
| 設定のときにメール・コード・パスワードをまとめて送る | API が1本減る | パスワードの長さ違いで入り直すたびにコードの入力回数を使う |
| **未登録にも案内メールを送る（採用）** | 応答・処理量・その後のコード確認の応答が揃う。利用者は登録していないと分かる | 使われないコードの行ができる |
| 未登録には何も送らない | 送信数が減る | 処理量の差で所要時間から登録の有無が分かりうる。利用者は届かない理由が分からない |
| **設定後にこの端末でログイン（採用）** | デザインの遷移（Main へ）と一致。すぐに使える | — |
| 設定後はログイン画面に戻す | セッション発行の処理が要らない | もう一度パスワードを入力させる手間。デザインと食い違う |
| **停止・失効は設定時に理由を返して断る（採用）** | コードで本人確認済みの相手にだけ状態を伝える（ADR 0009 と同じ考え）。使えないアカウントの状態を変えない | — |
| パスワードは変えて、ログインだけ断る | 停止解除後に新しいパスワードで使える | 使えないアカウントの資格情報を変えることになり、既存セッションの扱いもあいまいになる |
