# ADR 0051: 教職員の利用条件を決める

- 日付: 2026-11-04
- 状態: 採用（[ADR 0007](0007-signup-flow.md) の「教職員・留学生は `^\d{8}@edu…` だけを受け付ける」のうち教職員の部分を置き換える）
- 関連する章ID: AUTH-5, ADMIN, AUTH-1, AUTH-3, AUTHN-2, AUTHN-8, CARD, DEAL-1, BROWSE, API

## 背景

AUTH-5（教職員の利用）は「教職員用の画面とAPIは学生用と分ける」「数字以外のアドレスも受け付ける」という前提だけで検討を保留していた。未決事項「教職員の利用条件（受け付けるメールドメイン、学生との判定方法、取引成立時に開示する情報、出品時の確認書類、アカウントの有効期限）」（[product/open-questions.md](../product/open-questions.md)、#129）を決めないと、server・app の作業に入れない。

教職員は学籍番号を持たないため、学生で学籍番号に頼っていた次の点の代わりが必要だった。

- 学生かどうかの判定（`^\d{8}@edu\.cc\.saga-u\.ac\.jp$`）
- 有効期限の計算（入学年度＋在学年限）と学部・入学年度の表示
- 出品者の審査（学生証の番号と学籍番号の照合）
- 取引成立時の開示（学籍番号）

## 決定

- **ドメイン**：教職員用の画面で @より前を入力し、`@cc.saga-u.ac.jp` と `@edu.cc.saga-u.ac.jp` からドメインを選ぶ。サーバーでは `^[a-z0-9._+-]{1,64}@(edu\.)?cc\.saga-u\.ac\.jp$`（小文字に正規化）に一致し、学生の形式に一致しないものだけを受け付ける。
- **学生との区別**：アドレスの形式と経路で決める。学籍番号の形は学生用、それ以外は教職員用のAPIだけが受け付け、もう一方に入れたら形式違いとして扱う。1つのアドレスは学生か教職員のどちらか一方になる。登録の有無を判別させない方法は学生と同じ。
- **分ける範囲**：新規登録・ログイン（再確認を含む）・パスワードの再設定・身分証の提出を教職員用の画面とAPI（`/api/staff/**`）に分ける。一覧・出品・取引・売上・マイページは共通で、利用者の種別（`student`／`staff`）に応じて表示を変える。セッション・送信数や入力ミスの制限は共通。
- **有効期限**：新規登録と、コードで確認するたび（再確認・パスワードの再設定）に「確認した日の1年後以降で最初の3月31日」に更新する（今の有効期限のほうが遅ければ変えない。管理者が延ばした期限を縮めないため）。過ぎたら学生と同じく日次ジョブで失効させ、同じ後処理をする。失効したアカウントは戻さない。
- **学部・入学年度**：持たない。出品者や購入希望者の表示は「教職員」だけにし、学部の絞り込みに含めない。
- **出品の確認**：職員証などの身分証なら種類を問わない。学生証と同じテーブル・バケット・審査・閲覧記録・保持期間（失効・削除から3年）で扱い、学籍番号は照合しない。
- **取引成立時の開示**：学籍番号の代わりにメールアドレスを開示する。開示の時期・条件は学籍番号と同じ。
- **管理者**：許可リスト（`ADMIN_STUDENT_NUMBERS`。名前は変えない）に教職員のメールアドレスも書けるようにし、学籍番号かメールアドレスのどちらかが一致すれば管理者とする（[ADR 0015](0015-admin-authorization.md) を広げる）。
- **管理画面**：ユーザーの検索は学籍番号かメールアドレスで行い、一覧の学籍番号・学部の欄には教職員ならメールアドレスと「教職員」を出す。身分証は学生証と同じ審査待ちの一覧に種別付きで並べる。
- **画面のデザイン**：キャンバスに教職員用の画面がないため、既存の Login・SignUp・Code・Password・Recheck・StudentCard の部品で組み、学生用ログイン画面から「教職員の方はこちら」で移れるようにする（[ADR 0035](0035-admin-screens-design.md) と同じ考え）。

## 理由と検討した選択肢

**学籍番号の形の `@edu` アドレスを教職員用で受け付けるか**

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| 断って学生用へ案内する（採用） | 学生が教職員として登録して有効期限・審査を逃れることがない。アドレスから種別が一意に決まる | `@edu` を持つ教職員が学籍番号の形だった場合に登録できない（想定しにくい） |
| 受け付ける | 経路を選べば何でも登録できる | 学生が教職員として登録できてしまう |

**有効期限**

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| コード確認のたびに「1年後以降で最初の3月31日」（採用） | 普段使う人は30日ごとの再確認で自動的に延び、年度末に特別な操作がいらない。使わなくなった人の商品は最長2年弱で取り下げられる | 退職してもすぐには失効しない（メールが使えなくなり30日でログインできなくなる） |
| 3月中に再確認させて翌年3/31へ延長 | 年度の区切りがはっきりする | 3月にログインしなかった人が失効し、復帰の仕組みが別に要る |
| 期限なし | 単純 | 退職した人の商品が管理者が止めるまで残る |

**出品の確認書類**：職員証に限ると持っていない教職員（非常勤など）が出品できないため、身分証なら種類を問わないことにした。

**取引成立時の開示**：連絡に使う Teams で相手を探せるメールアドレスにした。教職員のアドレスは氏名を含むことが多いが、開示は取引成立時だけで、規約・プライバシーポリシーに明記する。
