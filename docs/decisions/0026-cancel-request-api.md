# ADR 0026: キャンセルの申請・同意・取り下げの API と、キャンセル回数の数え方

- 日付: 2026-10-25
- 状態: 採用
- 関連する章ID: DEAL-4, JOBS-2, DB

## 背景

#29 で取引成立後のキャンセル（[DEAL-4](../product/05-deal-flow.md)）を実装するにあたり、次のことが決まっていなかった。

- [DealCancel](../design/screens/DealCancel.dc.html) の「同意しない」ボタンで、サーバー側が何かをするか（申請を断る操作を作るか）。
- 申請と同意を別の操作にするか。申請の取り下げをどう扱うか。
- DEAL-4「キャンセルの回数を記録し」の記録のしかた（[AdminUsers](../design/screens/AdminUsers.dc.html) に「キャンセル回数」が出る）。
- キャンセルしたときに、未使用の受け渡しトークンを無効にするか。

## 決定

- 申請と同意は同じ操作 `POST /transactions/{id}/cancel` にする。当事者の自分の同意日時（`buyer_cancel_agreed_at`・`seller_cancel_agreed_at`）を記録し、双方がそろったら同じトランザクションで取引をキャンセルにし、返金（モック）を記録し、商品を公開中に戻す。取引中のまま自分が同意済みなら、最初の日時のまま返す。キャンセルが成立した後に送り直したときは、取引中でないので 409 になる。商品が取引中でない場合（管理者による停止など）は、商品のステータスを変えずにキャンセルと返金を進める（受け渡し完了のときと同じ扱い）。
- 申請の取り下げは `POST /transactions/{id}/cancel/withdraw` で、自分の同意日時を消す。相手が同意した後（キャンセル済み）はできない。
- 「同意しない」は画面を閉じるだけで、API は作らない。申請は、申請した側が取り下げるまで残る。
- キャンセルの回数は列を足さず、キャンセルになった取引から数える。申請した人は同意日時の早い方で分かる。誰の回数として数えるか（双方か申請者だけか）は管理画面の issue で決める。
- キャンセルのときに受け渡しトークンは無効にしない。受け渡しの完了は取引中であることを条件付きUPDATE で確かめるので、キャンセル後のトークンは使えない（期限切れのトークンの削除は [JOBS-1](../tech/jobs-payment-mock.md)）。
- キャンセルの申請中でも、購入者は受け渡しを完了できる。完了した後はキャンセルできない。
- キャンセルした後も、相手の学籍番号は見せたままにする（開示を取り消さない。[DEAL-1](../product/05-deal-flow.md) は承認前の非開示だけを決めている）。

## 理由と検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| 申請と同意を同じ操作にする（採用） | 双方が同時に申請しても自然にキャンセルになる。条件付きUPDATE 2本で済む | 画面側で「申請」と「同意」の文言を相手の同意日時から出し分ける |
| 申請と同意を別の操作にする | 操作の意味が API で分かる | 同時に申請したときの扱いが要る |
| 「同意しない」を API にする | 申請した側に断られたことが分かる | デザインに断られた状態の表示がない。Teams で相談する前提（DEAL-4 の文言）と合わない |
| 回数を取引から数える（採用） | スキーマ変更が要らない。数え方を後から変えられる | 集計のたびに数える |
| 申請者の列を足す | 申請者がはっきりする | 取り下げ・再申請のときの扱いが増える |
