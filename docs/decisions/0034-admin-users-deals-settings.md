# ADR 0034: 管理者によるユーザー・出品・取引・手数料率の操作

- 日付: 2026-10-28
- 状態: 採用
- 関連する章ID: ADMIN, DEAL-4, AUTH-3, PAY-2, DATA

## 背景

管理画面（[AdminUsers](../design/screens/AdminUsers.dc.html)・[AdminDeals](../design/screens/AdminDeals.dc.html)・[AdminSettings](../design/screens/AdminSettings.dc.html)）の API を作るにあたり、次が決まっていなかった。

- ADMIN「取引状況の確認と、キャンセル・返金（モック）の手動対応」が、DEAL-4「取引成立後のキャンセルは双方の同意のみ」と両立しない。
- ADMIN「退学申請の受け付け」の申請をどこで受けて、何を記録するか。
- アカウントの停止と、退学による削除のときに、商品・取引・セッションをどうするか。
- DEAL-4 のキャンセル回数を誰の回数として数えるか（[ADR 0026](0026-cancel-request-api.md) で管理画面の issue に持ち越した）。
- 出品の停止をどのステータスからできるか、手数料率の「最終更新・管理者」をどう記録するか。

## 決定

- **管理者による取引のキャンセル**：DEAL-4 の例外に加える。対象は取引中の取引だけで、受け渡し完了後はできない。返金（モック）を記録し、商品は双方同意のキャンセルと同じく、取引中なら公開中に戻し、停止中ならそのままにする。当事者の同意日時は入れない。
- **キャンセル回数**：キャンセルになった取引のうち、購入者と出品者の同意日時が両方ある（双方同意で成立した）ものを、**両方の当事者**の回数に数える。失効・削除・管理者によるキャンセル（同意日時がそろわない）は数えない。
- **退学申請**：アプリから本人が申請する（申請の API と画面は別の issue）。申請日時を `users.withdrawal_requested_at` に記録し、管理画面では申請中のユーザーの件数と絞り込みを出す。
- **アカウントの停止**：有効 → 停止にし、セッションをすべて無効にする。商品は読み取り時に除かれ（[ADR 0018](0018-browse-visible-items.md)）、取引はそのまま残す（必要なら管理者が個別にキャンセルする）。**停止の解除**（停止 → 有効）もできる。
- **退学による削除**：有効・停止 → 削除にし、失効と同じ後処理（[ADR 0033](0033-account-expiry-and-daily-job.md)：商品の取り下げ、購入希望の期限切れ、取引中の取引のキャンセルと返金、学生証の削除予定日を「削除日 + 3年」、セッションの無効化）を同じトランザクションで行う。削除日は操作した日（日本時間）とする。
- **有効期限の変更**：有効・停止のユーザーだけ。今日（日本時間）以降の日付にする。
- **出品の停止**：下書き・公開中・購入希望あり・取引中から停止にできる。購入希望ありなら承認待ちの購入希望をすべて却下して枠を解放する（取り下げと同じ。[ADR 0022](0022-deal-request-item-status-and-approval-deadline.md)）。取引中なら取引は続ける（受け渡し完了・キャンセルは商品のステータスを変えずに進む。[ADR 0024](0024-handover-token-flow.md)、[ADR 0026](0026-cancel-request-api.md)）。商品の停止の解除は作らない。
- **手数料率の変更**：0〜10000 ベーシスポイント。変更した管理者を `settings.fee_rate_updated_by` に記録し、更新日時とあわせて管理画面に出す。成立済みの取引の料率は変わらない（[ADR 0003](0003-fee-rate-applied-at-deal.md)）。
- 管理 API は、未ログイン・管理者でなければどれも 404 にする（[ADR 0015](0015-admin-authorization.md)）。

## 理由と検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| 管理者キャンセルを例外にする（採用） | トラブル時に預かった代金を返せる。ADMIN の要件どおり | DEAL-4 の例外が2つになる |
| 管理者キャンセルを作らない | DEAL-4 を変えない | 当事者が連絡を絶つと代金が止まる |
| キャンセル回数を双方に数える（採用） | 申請の順に関係なく、キャンセルに関わった回数が分かる | 申請された側も回数が増える |
| 申請者だけに数える | 責任のある側が分かる | 同時の申請や取り下げ・再申請で申請者があいまいになる |
| 退学申請をアプリで受ける（採用） | 管理者が申請を見落とさない。件数を画面に出せる | 申請の API と画面が要る |
| 退学申請をアプリ外で受ける | 実装が少ない | デザインの件数・絞り込みが出せない |
| 停止はセッションの無効化だけ（採用） | 解除すれば元どおりに使える | 停止中の人の取引が残る |
| 停止でも失効と同じ後処理をする | 取引が残らない | 解除しても商品・取引が戻らない |
