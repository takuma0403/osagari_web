# ADR 0023: 購入希望の一覧の画面のルートと、承認・却下・送信後の画面の動き

- 日付: 2026-10-25
- 状態: 採用
- 関連する章ID: DEAL-1, DEAL-2, FE-1

## 背景

購入希望・購入希望一覧・確認モーダルの画面（#26）を作るにあたり、デザイン（Request・DealRequests・DealConfirm）と仕様から次の点が読み取れなかった。

- 出品者が購入希望の一覧（DealRequests）を開くルートと入口。FE-1 の `/deals/:dealId` は取引ID だが、購入希望の一覧の API（`GET /items/{itemId}/requests`）は商品ID で取り、取引の応答（`Transaction.item`）には商品ID がない。
- 購入者が購入希望を送った後に移る画面（デザインの仮のつながりは DealRequests だが、これは出品者の画面）。
- 購入希望の却下の操作（API はあるが、デザインに却下のボタンがない）。
- 承認の前に確認を挟むか（デザインは「この人に決める」から直接 DealConfirm へ進む）。

## 決定

- 購入希望の一覧は **`/sell/:itemId/requests`**（商品ID）。入口は商品詳細で、自分の出品が購入希望ありのとき主ボタンを「出品を編集する」から「購入希望を見る」に替える（購入希望ありは編集できない。[ADR 0016](0016-item-edit-withdraw-rules.md)）。
- 購入者が購入希望を送ったら、商品詳細へ戻り（履歴は置き換える）「購入希望を送りました」のトーストを出す。購入者の取引の表示は取引一覧（#48）と取引詳細（#28）で扱う。
- 却下は購入希望ごとの text ボタン「見送る」で、確認ダイアログ（ConfirmDialog）で確かめてから行う。
- 承認も確認ダイアログで確かめてから行う（承認すると代金を預かり、ほかの購入希望は自動で却下され、一方的には取り消せないため。DEAL-1, DEAL-4）。承認できたら取引成立の確認モーダル（DEAL-2）を出し、「確認しました」で記録して `/deals/:dealId` へ進む。確認モーダルは「確認しました」を押すまで閉じない。

## 理由と検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| `/sell/:itemId/requests`（採用） | 既存の API だけで一覧と商品を取れる。出品の編集（`/sell/:itemId`）と同じく商品ID を使う | 取引詳細（`/deals/:dealId`）と URL が分かれる |
| `/deals/:dealId` に統合 | 取引詳細の画面が1つにまとまる | 取引の応答に商品ID を足す server の変更が先に要る |
| 送信後に商品詳細へ戻す（採用） | デザインのない購入者向けの承認待ちの画面を作らずに済む | 送った購入希望は取引一覧ができるまで画面から追えない |
| 却下・承認とも確認を挟む（採用） | 取り消せない操作の押し間違いを防ぐ | 1回分タップが増える |
