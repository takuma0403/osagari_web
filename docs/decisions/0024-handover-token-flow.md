# ADR 0024: 受け渡しトークンの照合と完了の API、完了リンクの形式、確認コードの完了方法

- 日付: 2026-10-25
- 状態: 採用
- 関連する章ID: DEAL-3, PAY-2, FE-1, API-1

## 背景

受け渡し完了の API（#27）を作るにあたり、仕様とデザイン（DealQR・DealScan・DealCompleteIssue・DealCompleteEnter）から次の点が読み取れなかった。

- DealCompleteEnter では「次へ」の時点でコードの誤り・リンクの無効を表示し、そのあと「商品を受け取りましたか？」で「受け取った」を押して完了する。トークンを使用済みにせずに照合だけする API が要るか。
- 完了リンクにトークンをどう載せるか（FE-1 で「DEAL-3 の実装で決める」としていた）。
- 受け渡しQRの下に表示する6桁の確認コードを手入力して完了したとき、完了方法（`handover_method`）を何として記録するか。
- 6桁のコードの入力に回数の制限を設けるか。

## 決定

- 照合と完了を別の API にする。`POST /transactions/{id}/handover/verify` は使用済みにせずに照合だけを行い、`POST /transactions/{id}/complete` で使用済みにして完了する。どちらも購入者だけが呼べる（ほかの人は 404）。使えないトークンは 400 `invalid_handover_token`。
- 完了リンクと受け渡しQRの中身は `/deals/{取引ID}/complete#t=<トークン>`（URL のフラグメント）。サーバーはトークンだけを返し、URL はアプリが組み立てる。
- 受け渡しQRは、QR のトークンと6桁の確認コードを1つの受け渡しトークンとして発行する（有効期限5分）。完了リンク（トークン）と完了コード（6桁）は別々に発行する（有効期限24時間）。同じ取引・同じ種類を発行し直したら、それまでの未使用のものは使えなくする。
- 完了方法は購入者の入力の種類で記録する。QR の下の確認コードを入力したときも `code` にする。
- 6桁のコードの入力に回数の制限は設けない。
- 完了のときに商品が取引中でなければ（管理者の停止など）、商品のステータスはそのままにして取引の完了は止めない（購入者が受け取った後に代金が預かられたまま止まらないようにするため）。

## 理由と検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| 照合と完了の API を分ける（採用） | デザインどおり「次へ」でエラーを出せ、「受け取った」の前にリンクが使えないことが分かる | API が1本増える |
| 完了の API だけ | API が少ない | 「受け取った」を押した後にエラーが出て、デザインとずれる |
| フラグメントで載せる（採用） | トークンがサーバー・Hosting のアクセスログやリファラーに残らない | アプリでの読み取りが少しだけ手間 |
| クエリ文字列で載せる | 扱いが単純 | アクセスログなどに残りうる |
| 確認コードを `code` として記録（採用） | 実際の操作（手入力）が分かる | 発行元（QR の画面）は記録に残らない |
| 確認コードを `qr` として記録 | 発行元が分かる | 手入力とカメラの読み取りを区別できない |

コードの入力回数を制限しないのは、照合できるのがその取引の購入者だけで、総当たりで完了させても購入者が自分の代金を出品者に払うだけになり、得をする人がいないため。
