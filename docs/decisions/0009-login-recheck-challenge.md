# ADR 0009: ログインの再確認チャレンジと、利用できないアカウントの応答

- 日付: 2026-10-14
- 状態: 採用
- 関連する章ID: AUTH-1, AUTH-3, AUTHN-2, AUTHN-3, AUTHN-5, API-1

## 背景

#10（ログイン・再確認API）を実装するにあたり、仕様に書かれていない次の点を決める必要があった。

- AUTHN-3 は「パスワードが一致したら、30日経過か初めての端末ならメールでコードを送り、入力されたらログインできる」とだけ書いている。パスワードを確かめた後のコード入力を、どうやって同じ本人・同じログインの手続きに結びつけるかが決まっていない。
- パスワードは合っているが、停止中・失効（有効期限切れ）・削除済みのアカウントにどう応答するかが決まっていない。一方で AUTHN-2 は登録の有無を判別させないことを求めている。
- 30日経過と初めての端末の両方に当てはまるとき、Recheck 画面にどちらの理由を出すか。
- ログアウトや、ログイン状態の確認（自分の情報の取得）の細部。

## 決定

- **再確認はログインチャレンジで結びつける**（ユーザーが選択）。パスワードが一致して再確認が必要なとき、新しいテーブル `login_challenges`（user_id, token_hash, reason, device_hash, expires_at, consumed_at）にチャレンジを作り、`202` でトークンを返す。値は256ビットの乱数で、DB には SHA-256 だけを持つ（[ADR 0006](0006-auth-secret-hashing.md)）。有効期限は **15分**、`consumed_at IS NULL AND expires_at > now` を条件にした UPDATE で一度だけ使える。コードの確認（`POST /auth/login/recheck/verify`）と再送（`POST /auth/login/recheck/codes`）はこのトークンで行い、パスワードを再び送らせない。
- コードは既存の `verification_codes`（purpose = `login_recheck`、10分有効、入力ミス5回まで・照合前に数える）を使う。再送すると古いコードは使えなくなる。
- ログイン時の端末識別子（`X-Device-Id`）のハッシュをチャレンジに保存し、コードの確認に成功したらその端末を登録する。確認時のリクエストのヘッダーは使わない。ヘッダーがなかった場合は端末を登録しない（次回も初めての端末として扱う）。
- コードの確認に成功したら、チャレンジの消費・最後の確認日時（`users.code_verified_at`）の更新・端末の登録・セッションの発行を1つのトランザクションで行う。コードの使用済み化はその前に（新規登録と共通の照合処理で）行うため、このトランザクションが失敗するとコードだけが消費される。その場合はコードを再送すれば続けられる。
- 再確認の理由は `code_expired`（最後のコード確認から30日以上）と `new_device`（初めての端末）。**両方に当てはまるときは `code_expired`** にする（端末が登録済みでも再確認が要るため）。
- **利用できないアカウントの応答**（ユーザーが選択）：
  - メールアドレスの形式違い・未登録・**削除済み**・パスワード違いは区別せず、`401 invalid_credentials` を返す。未登録・削除済みでもダミーのハッシュに対して argon2id の照合を行い、所要時間を揃える。長さが範囲外のパスワードは照合せずに同じエラーにする（登録済みのパスワードと一致しえないため）。
  - パスワードが一致したときだけ、**停止中は `403 account_suspended`、失効は `403 account_expired`** で理由を示す。失効は `status = expired` のほか、日本時間の日付が有効期限（`expires_on`、その日の終わりまで使える）を過ぎた場合も含める。日次ジョブが状態を変える前でも期限切れのアカウントは使えない。
- **セッションの検証**：OpenAPI で `security: []` を付けた操作以外はすべて `__session` を必須にする。サーバーは埋め込んだ API 契約からセッション不要な操作を読み取り、ミドルウェアで検証する。有効なのは、失効しておらず期限内（30日）のセッションで、ユーザーが `active` かつ期限内のときだけ。それ以外は `401 unauthorized`。セッションの有効期間は延長しない（発行から30日）。
- **ログアウト**（`POST /auth/logout`）はいまのセッションだけを失効させ、Cookie を消す。未ログイン・失効済みでも `204` を返す（冪等）。
- 機能固有のエラーコード `invalid_credentials`（401）・`account_suspended`（403）・`account_expired`（403）・`invalid_login_challenge`（400）を追加する。

## 理由と検討した選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| **ログインチャレンジ（採用）** | パスワードを一度しか送らない。再送も本人の手続きに限れる。端末をログイン時の値に固定できる | テーブルが1つ増える |
| コード確認のたびにメール・パスワードも送る | テーブルが増えない | app がパスワードを画面間で持ち続ける。確認のたびに argon2id を2回計算する |
| 停止・失効もパスワード違いと同じ応答 | 状態を一切明かさない | 利用者は理由が分からず、パスワード再設定を繰り返してしまう |
| **パスワード一致時だけ理由を示す（採用）** | 本人には理由が分かる。パスワードを知らない人には状態も登録の有無も分からない | — |
| 停止・失効を1つのエラーにまとめる | コードが少ない | 失効（卒業）と停止（管理者の対応）で利用者の取るべき行動が違う |
| 両方当てはまるときは `new_device` | 端末の登録を促す文言になる | 登録済みの端末でも出る `code_expired` と区別が付きにくい |
